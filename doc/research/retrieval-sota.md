# Retrieval for an LLM "librarian" over a heterogeneous private corpus — state of the art, mid-2026

*Compiled 2026-08-26. Scope: a few hundred MB of chat logs, mailing-list archives, a wiki with history, versioned reference books, and a dictionary with change history.*

**How to read this document.** Every claim tagged **[verified]** was read from a fetched primary source (URL + date given). Claims tagged **[secondhand]** come from search-result summaries or secondary write-ups where the primary page could not be fetched (arXiv, Medium and several blogs were blocked from this environment). Claims tagged **[inference]** are my own synthesis and are not sourced.

---

## Consensus summary as of mid-2026

1. **Retrieval is a tool the agent calls in a loop, not a one-shot pre-processing step.** Anthropic's "just-in-time" context loading (Sep 2025), A-RAG (Feb 2026), Direct Corpus Interaction (May 2026) and LogicalRAG (May 2026) all converge on: give a capable model a small set of *high-resolution* retrieval primitives (exact/boolean lexical search, "read this span", optional semantic search) and let it iterate. The 2023-2024 "embed everything, top-k, stuff, answer" pipeline is now considered a baseline, not a design. [verified, see §1]
2. **Lexical search is the primary primitive; embeddings are a secondary tool, not the foundation.** Amazon Science (AAAI 2026) got >90% of RAG performance with keyword tools and no vector store; DCI beat embedding retrieval by 11-30 points on agentic benchmarks. But Cursor (Nov 2025) and LlamaIndex (Jan 2026) both showed that adding semantic search on top of grep helps as corpora grow. Net: **hybrid, with lexical first**. [verified, §1]
3. **When embeddings are used, hybrid BM25 + dense fused by RRF, followed by a cross-encoder reranker, is the boring default that everyone ships.** Learned sparse (SPLADE/ELSER) is a drop-in upgrade to BM25 on the engines that support it; late-interaction (ColBERT/ColPali) is deployed mainly for PDF/image pages, not plain text. [verified/secondhand, §2]
4. **Chunking: structure-aware, plain, contextualised with a document-level header.** Contextual chunk headers (Anthropic, Sep 2024) held up; proposition/atomic-fact indexing, embedding-based "semantic chunking", LLM-guided chunking and even chunk overlap did not (Feb 2026 taxonomy paper; Jan 2026 analysis). Hierarchical summaries (RAPTOR-style) survived as a way to answer "global" questions. [verified, §3]
5. **Full GraphRAG is judged overkill for most corpora; lightweight entity/timeline structure is not.** LazyGraphRAG (Nov 2024) cut indexing cost to 0.1% of GraphRAG; HippoRAG 2 (Feb 2025) showed GraphRAG uses ~12x the tokens of a plain embedding baseline; GraphRAG-Bench (ICLR 2026) found graphs tie plain RAG on fact lookup and win only on multi-hop/summarisation; a June 2026 practitioner rule of thumb says graphs earn their cost only when ≥15% of traffic is relational. Temporal/bi-temporal facts (Zep/Graphiti, VersionRAG) are the part that matters for "how did X come to be" questions. [verified, §4]
6. **Long context + prompt caching is a real substitute for retrieval on *small, stable, heavily-queried* references, and a bad one for everything else.** 1M context at standard pricing (Anthropic, Mar 2026) and 0.1x cache reads make "whole dictionary in a cached prefix" affordable, but Chroma's context-rot study (Jul 2025), NoLiMa (ICML 2025) and a June 2026 long-horizon-search study show quality degrades with input length even when it "fits". Anthropic's own guidance: under ~200K tokens, skip RAG; above it, retrieve. [verified, §5]
7. **Deep-research pattern: one orchestrator with persistent state, read-only parallel subagents, a single writer, a separate citation/verification pass.** Anthropic (Jun 2025), LangChain (Jun/Jul 2025), Cognition (Apr 2026) agree. Two 2026 papers show multi-agent gains largely disappear at equal token budgets, so subagents are a *context-isolation and parallelism* device, not an intelligence multiplier. Citation grounding is still weak: frontier deep-research agents produce 94%+ working links but only 39-77% factually-supported citations (May 2026). [verified, §6]
8. **Evaluation: error analysis first, binary judges validated against humans, corpus-generated question sets.** Generic RAGAS-style scores out of the box are considered false confidence (Hamel Husain, May 2025; case-aware judge paper, Feb 2026). Citation precision/recall (ALCE-style) and three-part citation checks (link works / relevant / fact-supported) are the 2026 citation metrics. [verified, §7]
9. **Design around the corpus, not around a SaaS.** Snyk's Slack RAG (May 2025), VersionRAG (Oct 2025), Zep's bi-temporal model (Jan 2025) and LlamaIndex's per-index routing (May 2025) all beat generic pipelines by shaping the index to the data (threads → Q&A units, versions → version graph, facts → validity intervals). Managed "throw docs at it" products (Claude Projects RAG, OpenAI vector stores, Cloudflare AI Search, Vertex RAG Engine, LlamaCloud, Ragie) are fine for flat document piles and structurally wrong for versioned/threaded/temporal corpora. [verified/secondhand, §8]

## 1. Agentic retrieval vs. classic vector RAG

**What the primary sources say.**

- Anthropic, *Building effective agents* (2024-12-19): retrieval is one augmentation of the "augmented LLM"; "finding the simplest solution possible, and only increasing complexity when needed." <https://www.anthropic.com/engineering/building-effective-agents> [verified]
- Anthropic, *Effective context engineering for AI agents* (2025-09-29): names "just-in-time" context loading—agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and load on demand; warns runtime exploration "is slower than pre-computed retrieval" and needs "opinionated and thoughtful engineering" to stop agents "chasing dead-ends"; endorses a **hybrid**: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time." Sub-agents return "a condensed, distilled summary of its work (often 1,000-2,000 tokens)." <https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents> [verified]
- The widely-quoted Boris Cherny line ("Early versions of Claude Code used RAG + a local vector db, but we found pretty quickly that agentic search generally works better…") appears in Sourcegraph's 2026 context-engineering guide and several Medium posts; I could not fetch the original post. [secondhand] <https://sourcegraph.com/blog/context-engineering>
- Amazon Science, *Keyword search is all you need: Achieving RAG-level performance without vector databases using agentic tool use* (AAAI 2026): "tool-based keyword search implementations within an agentic framework can attain over 90% of the performance metrics compared to traditional RAG systems without using a standing vector database." <https://www.amazon.science/publications/keyword-search-is-all-you-need-achieving-rag-level-performance-without-vector-databases-using-agentic-tool-use> [verified]
- *Beyond Semantic Similarity: Rethinking Retrieval for Agentic Search via Direct Corpus Interaction* (arXiv 2605.05242, 2026-05-03): agents given "grep, file reads, shell commands, lightweight scripts" over raw corpora scored 80.0 vs 69.0 (BrowseComp-Plus), 83.0 vs 52.3 (HotpotQA/MuSiQue), NDCG@10 68.5 vs 47.0 against embedding retrieval; framing is *localization* (agentic) vs *coverage* (embeddings). <https://www.alphaxiv.org/overview/2605.05242> [verified via alphaXiv summary]
- *Rethinking Agentic RAG: Toward LLM-Driven Logical Retrieval Beyond Embeddings* (arXiv 2605.27123, 2026-05-26): LLM writes Boolean/phrase/BM25 queries against a plain inverted index; "matches a strong agentic hybrid baseline while substantially reducing construction and serving cost" and "substantially reduces hallucinations"; concedes embeddings "may still offer advantages in scenarios requiring highly abstract semantic matching or fuzzy associations." <https://arxiv.org/abs/2605.27123> [secondhand]
- *A-RAG: Scaling Agentic RAG via Hierarchical Retrieval Interfaces* (arXiv 2602.03442, Feb 2026): three tools—keyword search, semantic search, chunk read—"surpasses existing graph-RAG and workflow-based methods across four multi-hop QA benchmarks" with "comparable or fewer tokens"; "even a naive single-tool variant outperforms complex predefined workflows." <https://huggingface.co/papers/2602.03442> [verified]
- *Fishing for Answers* (arXiv 2509.04820, Sep 2025): on legal/government documents, top-k "frequently misses golden chunks"; an iterative reasoning-agent loop that refines queries over turns is the proposed fix. <https://arxiv.org/abs/2509.04820> [secondhand]

**The counter-evidence (embeddings still earn their keep).**

- Cursor, *Improving agent with semantic search* (2025-11-06): a trained code embedding model added to grep gives "on average 12.5% higher accuracy in answering questions (6.5%-23.5% depending on the model)", most valuable in codebases with 1,000+ files. <https://cursor.com/blog/semsearch> [verified]
- LlamaIndex, *Did filesystem tools kill vector search?* (2026-01-13): on 5 papers a Gemini-3-Flash filesystem agent beat RAG on correctness (8.4 vs 6.4/10) but was slower (11.2 s vs 7.4 s); at 100-1,000 abstracts RAG was "substantially" faster and "slightly" more correct. <https://www.llamaindex.ai/blog/did-filesystem-tools-kill-vector-search> [verified]
- LightOn, *RAG is dead, long live RAG* (2025-11-12): "You can't grep a diagram"; retrieval should be a conditional policy (IF / WHAT / WHERE-HOW / GENERATE). <https://lighton.ai/lighton-blogs/rag-is-dead-long-live-rag-retrieval-in-the-age-of-agents> [verified]
- RAGFlow, *From RAG to Context* (2025-12-22): index-free grep "applicable only to well-organized, pure-format, fixed-terminology codebases". <https://ragflow.io/blog/rag-review-2025-from-rag-to-context> [verified]
- Reports that Vercel replaced its RAG pipeline with filesystem + bash at 75% lower cost circulate on Medium (2026); I could not fetch a Vercel primary. [secondhand, unverified]

**Consensus for non-code natural-language corpora [inference from the above].** Lexical search wins where queries contain names, dates, IDs, quoted phrases, or the agent can *guess vocabulary* (a dictionary, a wiki, a mailing list with consistent jargon). Embeddings win where the user's wording and the corpus wording diverge (chat logs with slang/typos, "what was the argument for…" questions) and for *coverage* of a broad topic. For a few-hundred-MB corpus the practical answer in 2026 is: an FTS/BM25 index with metadata filters as the primary tool, a semantic-search tool as a secondary tool the agent may call, and an agent loop with a bounded tool budget. The "RAG vs agentic" framing is dead; what remains is *which primitives you expose and how iterative the loop is*.

## 2. Hybrid retrieval and reranking

- **Hybrid + RRF is the deployed default.** Elastic's ELSER post (2023-06-21) already recommended "an ensemble of statistical (à la BM25) and model based retrieval" fused with RRF that "performs well without calibration." <https://www.elastic.co/search-labs/blog/elastic-learned-sparse-encoder-elser-retrieval-performance> [verified]. 2026 practitioner references describe the same shape: parallel BM25 + ANN, top-50…500 each, RRF, then cross-encoder over the top-50…200. <https://www.digitalapplied.com/blog/hybrid-search-bm25-vector-reranking-reference-2026>, <https://denser.ai/blog/hybrid-search-for-rag/> [secondhand]
- Anthropic's Contextual Retrieval numbers (2024-09-19) remain the canonical evidence chain: contextual embeddings alone cut top-20 retrieval failure 35% (5.7%→3.7%); adding contextual BM25 49% (→2.9%); adding a reranker 67% (→1.9%). <https://www.anthropic.com/engineering/contextual-retrieval> [verified]
- **Rerankers.** ZeroEntropy's guide (2025-08-21): optimal candidate set 50-75 for most apps, plateau past 100; cross-encoders 200 ms-2 s, LLM rerankers 1-3 s+ and $0.50-$5/M tokens—"better suited for offline batch processing". <https://zeroentropy.dev/articles/ultimate-guide-to-choosing-the-best-reranking-model-in-2025/> [verified]. Cohere Rerank 4 (Pro/Fast) shipped ~Dec 2025 (+170 ELO over 3.5; #2 behind zerank-2) <https://agentset.ai/blog/cohere-reranker-v4> (2025-12-13) [verified]. `BAAI/bge-reranker-v2-m3` is the standard self-hosted choice [secondhand, multiple 2026 lists]. A common 2026 heuristic: "Add a reranker when Recall@50 is meaningfully better than Recall@5… Reranking solves precision, not recall — fix the retriever first." <https://redis.io/blog/top-reranking-models-rag-accuracy/> [secondhand]
- **Learned sparse (SPLADE/ELSER/miniCOIL).** Natively supported in Elasticsearch, Qdrant (FastEmbed) and Vespa as of 2026; Elastic's recommended high-recall config is BM25 + ELSER + dense kNN under one RRF retriever. <https://www.premai.io/blog/hybrid-search-for-rag-bm25-splade-and-vector-search-combined/> [secondhand]. Treat it as "BM25 with synonyms" — worthwhile if your engine has it, not worth adding an engine for. [inference]
- **Late interaction (ColBERT/ColPali).** Research momentum is real (first LIR workshop at ECIR 2026, arXiv 2511.00444, Nov 2025; PyLate tooling) [secondhand], but RAGFlow's year-end review places production use in *multimodal* RAG ("ColPali outputs 1024 tokens per page image") [verified]. For a text corpus of this size, a cross-encoder reranker over hybrid candidates captures most of the benefit at far lower index size. [inference]

## 3. Chunking and indexing

- **Contextual chunk headers (Anthropic, 2024-09-19)** held up. One-time cost "$1.02 per million document tokens" with prompt caching; a 2025 reproduction with Jina-v2 "confirms the original findings" that contextualized chunks beat pre-embedding chunks across datasets [verified for Anthropic; secondhand for the reproduction, <https://arxiv.org/pdf/2505.24782>]. *Reconstructing Context* (arXiv 2504.19754, Apr 2025): contextual retrieval "preserves semantic coherence more effectively but requires greater computational resources"; late chunking is cheaper but "tends to sacrifice relevance and completeness." <https://arxiv.org/abs/2504.19754> [secondhand]
- **Late chunking (Jina, 2024-08-22; paper v3 2025-07)**: consistent but small gains (SciFact nDCG@10 66.1 vs 64.2; +1.5-1.9 pts absolute in the v3 ablations). <https://jina.ai/news/late-chunking-in-long-context-embedding-models/> [verified]; <https://arxiv.org/pdf/2409.04701> [secondhand]. The Feb 2026 taxonomy shows it *degrades* in-document retrieval 3-53%. [verified below]
- **The 2026 taxonomy result.** *Beyond Chunk-Then-Embed* (arXiv 2602.16974, 2026-02-19): "optimal chunking strategies are task-dependent"; for in-corpus retrieval, "simple structure-based methods (paragraph or fixed-size chunking) outperform sophisticated alternatives, showing 15-27% better performance than proposition-based approaches"; paragraph/fixed/sentence differ by only 1-3% and all "significantly outperform LLM-guided alternatives"; chunk size correlates weakly (0.08-0.18) with in-corpus effectiveness. <https://www.alphaxiv.org/overview/2602.16974> [verified via alphaXiv]
- **Practitioner defaults (Firecrawl, updated 2026-02-24)**: recursive structure-aware splitting at 400-512 tokens; 256-512 for factoid queries, 1024+ for analytical; overlap no longer recommended. <https://www.firecrawl.dev/blog/best-chunking-strategies-rag> [verified]
- **Hierarchical / summary indexes.** RAGFlow's 2025 review names "TreeRAG & hierarchical approaches" as winners for resolving "local semantic breaks caused by physical chunking" [verified]. RAPTOR-style trees remain a research baseline (G-RAPTOR, DTCRS, SproutRAG in 2026) [secondhand]. The cheap 2026 form is: one LLM-written summary per document/thread/version plus contextual headers per chunk, with the agent reading summaries first. [inference]
- **Version-aware indexing.** *VersionRAG* (arXiv 2510.08109, Oct 2025): a hierarchical graph of version sequences, content boundaries and diffs; on 100 questions over 34 versioned technical docs it scored 90% vs naive RAG 58% and GraphRAG 64%. <https://arxiv.org/abs/2510.08109> [secondhand]. Directly relevant to the versioned books, wiki history and dictionary change log.

## 4. Graph-flavoured approaches

- **Microsoft GraphRAG (Apr 2024)** → **LazyGraphRAG (2024-11-25)**: indexing at "0.1% of the costs of full GraphRAG" (≈ vector-RAG cost), "outperforms all competing methods on local queries", and "comparable answer quality to GraphRAG Global Search" at "more than 700 times lower query cost", by deferring LLM work to query time and scaling via a single "relevance test budget". <https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/> [verified]. The current GraphRAG library docs list Global / Local / DRIFT / Basic search; I did not see a "lazy" mode on the docs page fetched. <https://microsoft.github.io/graphrag/> [verified]
- **HippoRAG 2** (arXiv 2502.14802, ICML 2025): passage nodes + query-to-triple matching + LLM "recognition memory"; +7% on associative-memory tasks, +9.5 F1 on 2Wiki, +3.1 on LV-Eval vs NV-Embed-v2. Cost table: GraphRAG 1,255% more tokens / 10.7 s per query; LightRAG 745% / 13.3 s; HippoRAG 2 ~100% / 1.2 s; plain embeddings 0.3 s. <https://huggingface.co/papers/2502.14802> [verified]
- **When graphs help (GraphRAG-Bench / "When to use Graphs in RAG", arXiv 2506.05690, ICLR 2026).** Four task levels: fact retrieval, complex reasoning, contextual summarisation, creative generation; the site states "GraphRAG frequently underperforms vanilla RAG on many real-world tasks." <https://graphrag-bench.github.io/> [verified]. Reported numbers (via VentureBeat 2026-08-02 and search summaries): fact retrieval a tie (60.9 vs 60.1), complex reasoning +10 (53.4 vs 42.9), contextual summarisation +13 (64.4 vs 51.3); multi-hop Recall@5 73.4%→87.8% with graphs. <https://venturebeat.com/orchestration/stop-graphing-everything-when-graphrag-actually-beats-vector-rag> [verified for the article; numbers secondhand from the paper]
- **Cost and judge-bias caveats (VentureBeat, 2026-08-02).** ~$48 with GPT-4o to build a graph for "a moderate corpus"; LLM-judge audits showed one method's "66.7% win rate fell to about 39%" after bias correction; recommendation: "route each query to the right method, or fuse evidence from both." [verified]
- **Break-even rule (Alok, 2026-06-29):** audit 200+ real queries; if relational queries are "under 15% of traffic, GraphRAG's benchmark advantage will not materialize"; "The graph is a cost center until proven otherwise." <https://aloknecessary.in/blogs/graph-rag-vs-rag/> [verified]
- **RAGFlow (2025-12-22)** lists pure GraphRAG as a 2025 loser: extracted entities/relations "often contain significant noise, redundancy, or errors" and cause "massive token consumption." [verified]
- **Temporal knowledge graphs.** Zep (arXiv 2501.13956, Jan 2025): bi-temporal edges (event time T, ingestion time T′), invalidation instead of deletion, episode/entity/community tiers; DMR 94.8% vs MemGPT 93.4%; LongMemEval +18.5% accuracy and 90% lower latency vs full-context baseline. <https://huggingface.co/papers/2501.13956> [verified]. Graphiti (open source) supports Neo4j, FalkorDB, Neptune (Kuzu deprecated) and keeps validity windows with provenance to source episodes. <https://github.com/getzep/graphiti> [verified]
- **Memory vs long context (arXiv 2603.04814, Mar 2026):** long-context GPT-5-mini had *better factual recall* than fact-memory systems on most benchmarks; memory wins on cost once history is long—"at approximately 100,000 tokens of context, the memory-based approach becomes more economical after roughly ten interaction turns." <https://www.alphaxiv.org/overview/2603.04814> [verified]

**Where this leaves "why/how did X come to be" questions [inference].** The evidence supports a *thin* structure layer rather than a full graph: (a) an entity table (people, terms, features, decisions) with aliases; (b) a timeline of dated events/edits per entity, each pointing at source spans (thread, mail, wiki diff, dictionary change); (c) bi-temporal validity on dictionary/wiki facts (VersionRAG/Zep style). The agent then answers historical questions by walking the timeline and reading the cited spans, which is exactly the "localization" strength of agentic search. Community summaries and LLM-extracted relation triples over the whole corpus are the parts judged overkill in 2026.

## 5. Long context + prompt caching as a retrieval substitute

**Prices and limits (Anthropic, current docs).** Cache reads 0.1x base input, 5-minute cache writes 1.25x, 1-hour writes 2x; max 4 breakpoints; minimum cacheable prefix 512-4,096 tokens depending on model; cache hits do not count against rate limits. Opus 4.6/4.8/5 $5 in / $0.50 cache-read; Sonnet 4.6 $3 / $0.30; Sonnet 5 $2 / $0.20; Haiku 4.5 $1 / $0.10 (per MTok). <https://platform.claude.com/docs/en/build-with-claude/prompt-caching> [verified]. 1M context became GA at standard pricing for Opus 4.6 and Sonnet 4.6 on 2026-03-13: "a 900K-token request is billed at the same per-token rate as a 9K one"; Opus 4.6 scores 78.3% on MRCR v2. <https://claude.com/blog/1m-context-ga> [verified]

**Anthropic's own threshold (2024-09-19):** "If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt", with caching cutting latency >2x and cost up to 90%. [verified]

**Quality evidence against "just stuff it".**
- Chroma, *Context Rot* (2025-07-14; Hong, Troynikov, Huber): 18 models; performance "degrades more quickly in input length with lower similarity needle-question pairs"; even one distractor hurts; "models perform better on shuffled haystacks than on logically structured ones"; on LongMemEval, focused ~300-token inputs beat ~113K full inputs, with Claude models showing "the most pronounced gap." <https://www.trychroma.com/research/context-rot> [verified]
- NoLiMa (ICML 2025; repo updated through Jul 2025 with GPT-4.1, Gemini 2.5, Llama 4, o3): at 32K, 10 of 12 models fall below 50% of their short-context baseline once literal keyword overlap is removed; GPT-4o drops from 99.3% to ~70-82% depending on paper version. <https://github.com/adobe-research/NoLiMa> [verified]
- *Diagnosing and Mitigating Context Rot in Long-horizon Search* (arXiv 2606.29718, 2026-06-30): accumulated context makes agents "directly give up or prematurely provide uncertain answers"; specific content, not raw length, triggers it; "combining context compaction with trimming achieved optimal cost-performance"; sub-agent isolation works "with capable models but underperformed with weaker ones." <https://huggingface.co/papers/2606.29718> [verified]
- *Don't Break the Cache* (arXiv 2601.06007, Jan 2026): on DeepResearch Bench agent sessions, caching cut API cost 45-80% and TTFT 13-31% across OpenAI/Anthropic/Google, but "naive full-context caching… can paradoxically increase latency"; put dynamic content last and keep tool results out of the cached block. <https://arxiv.org/abs/2601.06007> [secondhand]
- LightOn (2025-11-12): "RAG is 8-82× cheaper than long context approaches for typical workloads" (their model: 1,000-page KB, ~5 chunks/query, 100 queries/day). [verified]
- RAG-vs-CAG decision framing (FutureAGI, 2026): seven axes—corpus size, freshness, latency, cost shape, citation auditability, query distribution, tenant model; "CAG wins where corpora are small, stable, broadly queried, and shared." <https://futureagi.com/blog/rag-vs-cag-cache-augmented-generation-2026/> [secondhand; page could not be fetched]

**Worked cost comparison [inference, using the verified prices above].** A whole dictionary of ~300K tokens kept as a cached prefix on Sonnet 4.6 costs ≈ $0.09 per query in cache reads (300K × $0.30/M) plus a $1.13 write per cold start (300K × $3.75/M); the same question answered from ~6K retrieved tokens costs ≈ $0.02. So caching is ~4-5x more expensive per query but removes retrieval-miss risk and engineering. For a 1M-token reference book on Opus 4.6 the cached read alone is $0.50/query. Given the context-rot findings, the practical rule is: cache whole documents up to roughly the 100-200K range when queries are dense and the document is stable (a dictionary, a single reference book edition); above that, or when the question is "which of these 50 threads…", retrieve. Also note that prompt-caching TTL (5 min / 1 h) means a librarian that answers a few questions per day pays the write price repeatedly unless traffic is batched.

## 6. Deep-research / multi-hop agent patterns

- **OpenAI Deep Research** launched 2025-02-03 on an o3 variant, browsing 5-30 minutes; moved to a GPT-5.2-based model in Feb 2026 with MCP-server integration; OpenAI acknowledges it "occasionally makes factual hallucinations." <https://en.wikipedia.org/wiki/ChatGPT_Deep_Research> [verified]
- **Anthropic, *How we built our multi-agent research system* (2025-06-13):** orchestrator-worker; Opus lead + Sonnet subagents; +90.2% over single-agent Opus 4 on internal evals; ~15x the tokens of a chat; token usage explains 80% of variance; scaling rules (fact-check: 1 agent, 3-10 calls; comparison: 2-4 subagents × 10-15 calls; complex: 10+ subagents); "start with short, broad queries… then progressively narrow"; a separate citation agent "identif[ies] specific locations for citations"; not for tasks that "require all agents to share the same context"; eval by LLM-judge rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) plus human review. <https://www.anthropic.com/engineering/built-multi-agent-research-system> [verified]
- **Cognition**: *Don't Build Multi-Agents* (Jun 2025) → *Multi-Agents: What's Actually Working* (2026-04-22): working setups "share the same property: one main loop carries state, subagents are stateless workers with narrow scope"; "most multi-agent setups in the world are limited to 'readonly' subagents, like web search subagents and code search subagents"; a clean-context review agent catches ~2 bugs/PR; cost savings via asymmetric model pairs remain "an open problem." <https://cognition.com/blog/multi-agents-working> [verified]
- **LangChain**: *How and when to build multi-agent systems* (2025-06-16): multi-agent excels at "read-heavy" tasks; "conflicting write actions typically produce far worse outcomes than conflicting read actions." <https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems> [verified]. *Open Deep Research* (2025-07-16): Scope → Research (supervisor + parallel researchers) → Write; "Context isolation of sub-topics during research can avoid various long context failure modes"; sub-agents compress findings before returning. <https://www.langchain.com/blog/open-deep-research> [verified]. Successor harness `deepagents` (planning, filesystem, subagents, context compression) [secondhand].
- **Skeptical 2026 evidence.** Tran & Kiela, *Single-Agent LLMs Outperform Multi-Agent Systems on Multi-Hop Reasoning Under Equal Thinking Token Budgets* (2026-04-11): at matched budgets single agents match or beat MAS on FRAMES/MuSiQue; API-reported thinking tokens can exceed visible output 4.7x, inflating MAS claims; MAS helps when context is noisy. <https://www.alphaxiv.org/overview/2604.02460> [verified]. *Do More Agents Help?* (2026-06-04): "at most one of six tested MAS exceeds the matched single-agent anchor" (74.12%); a Claude-Code-style runtime-generated workflow hit 66.72% on GAIA, 20+ points over static MAS; success "depends less on agent quantity and more on task-aligned coordination mechanisms that include dynamic delegation, state management, and verification stages." <https://www.alphaxiv.org/overview/2606.05670> [verified]
- **Token-cost controls.** Anthropic *Advanced tool use* (2025-11-24): Tool Search Tool cuts tool-definition overhead ~85% (77K→8.7K tokens); Programmatic Tool Calling runs tool sequences in a sandbox and returns only distilled output—"average usage dropped from 43,588 to 27,297 tokens, a 37% reduction on complex research tasks." <https://www.anthropic.com/engineering/advanced-tool-use> [verified]. Server-side compaction and context editing exist on the API (beta) [verified via Anthropic docs]. Managed Agents' multiagent orchestration docs (2026) frame delegation as Parallelization / Specialization / Escalation ("Consult a more capable agent or model for a subset of complex subtasks") and use `claude-haiku-4-5` as the coordinator in examples, with per-thread cost at "the thread's own served model." <https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration> [verified]
- **Citation grounding.** Anthropic Citations API (2025-01-24): returns `cited_text` with document index and char/page locations—users "can confirm that quoted text did indeed come from the specified documents." <https://simonwillison.net/2025/Jan/24/anthropics-new-citations-api/> [verified]. *Cited but Not Verified* (arXiv 2605.06635, May 2026): frontier deep-research agents keep link validity >94% and relevance >80% but only 39-77% fact-check accuracy; models that cite more are *less* accurate (39-59%); accuracy "drops by approximately 42%… as tool calls scale from 2 to 150." <https://arxiv.org/abs/2605.06635> [secondhand]. DeepResearch Bench (Jun 2025; ICLR 2026) FACT citation accuracy ranged 78% (OpenAI DR) to 94% (Claude with search). <https://arxiv.org/abs/2506.11763> [secondhand]

**The 2026 loop, distilled [inference].** plan (brief + sub-questions) → parallel read-only search subagents with narrow scope and compressed returns → single writer with the orchestrator's state → *separate* citation/verification pass that re-opens each cited span and checks entailment (quote-verification, Citations-API style) → drop or flag unsupported claims. Keep subagents on cheaper models, cap tool calls per subagent (Anthropic's 3-15 range), compact + trim rather than accumulate.

## 7. Evaluation

- **Hamel Husain & Shreya Shankar, *LLM Evals FAQ* (2025-05-28):** "Error analysis is the most important activity in evals"; review ≥100 traces, stop when ~20 in a row yield no new failure category; prefer binary pass/fail ("Likert scales introduce significant challenges"); validate each LLM judge's TPR/TNR on a held-out human-labelled set and correct estimates; "Generic evaluations waste time and create false confidence"; for RAG, evaluate retrieval with Recall@k / Precision@k / MRR and generation with judged failure modes; generate synthetic queries along structured dimensions, not "give me test queries." <https://hamel.dev/blog/posts/evals-faq/> [verified]
- **Chroma, *Generative Benchmarking* (2025-04-07):** build the golden set from your own corpus—LLM-filter documents for answerability, then generate queries steered by real examples; public benchmarks are contaminated (11.9% of naive generated queries near-duplicate ground truth) and "strong performance on a public benchmark… does not guarantee comparable performance for your specific production pipeline." <https://www.trychroma.com/research/generative-benchmarking> [verified]
- **RAGAS** still defines the four-metric vocabulary (faithfulness as supported-claims/total-claims, answer relevance, context precision/recall); v0.4 (late 2025) extends to agentic workflows [secondhand, <https://benchmarkingagents.com/rag-eval/>]. Alternatives in 2026 tooling lists: DeepEval, Arize Phoenix, LangSmith, Braintrust, Maxim; benchmarks ARES, CRAG [secondhand].
- **Citation metrics.** ALCE-style citation recall (do the cited docs entail the sentence) and precision (does removing a doc break entailment) remain the standard [secondhand]; the May 2026 deep-research paper adds link-works / relevant / fact-supported as a three-part check [secondhand].
- **Judge design in 2026.** *Case-Aware LLM-as-a-Judge for Enterprise-Scale RAG* (arXiv 2602.20379, 2026-02-23): eight operational metrics, severity-aware scoring, strict JSON, and the finding that "generic proxy metrics provide ambiguous signals" for multi-turn workflows with structured identifiers. <https://www.alphaxiv.org/overview/2602.20379> [verified]. VentureBeat (2026-08-02) reports judge-bias corrections turning a 66.7% win rate into ~39% [verified].
- **Anthropic's practice (2025-06-13):** start with ~20 representative queries and an LLM judge with a rubric; small samples catch most regressions; keep humans in the loop for what the judge misses. [verified]

**Practice for this corpus [inference].** Build 50-150 questions by (a) mining real questions from the chat/mail archives, (b) generative-benchmarking the wiki/book/dictionary, (c) writing a dozen "how did X come to be" historical questions with hand-verified answer spans. Score binary: answered / grounded / cites-correct-span / correct-version-or-date. Tune retrieval (Recall@k on gold spans) separately from generation.

## 8. Corpus-shaped design and the generic products

**Evidence for shaping the index to the data.**
- Snyk, *From Slack threads to structured knowledge* (2025-05-27): thread-level chunking failed ("Threads varied significantly"); the fix was LLM extraction of Q&A pairs—"Each Slack thread asking a question and receiving a response became a single, structured document chunk"; "We embedded only the extracted questions" and served the stored answer. Heavy cleaning of user/channel IDs and markdown. <https://snyk.io/articles/from-slack-threads-to-structured-knowledge-implementing-rag-at-snyk/> [verified]
- VersionRAG (Oct 2025): version graph 90% vs naive 58% vs GraphRAG 64% [secondhand, §3]. Metadata-first filtering is now standard advice because "an outdated 2023 version may score higher in similarity than the correct 2025 document" [secondhand, <https://markaicode.com/rag-metadata-filtering-document-tags/>].
- Zep's bi-temporal model answers "what did we know about X as of date D" (Jan 2025) [verified, §4].
- LlamaIndex (2025-05-29): per-index auto-routed retrieval mode plus LLM-classified composite routing across multiple specialised indexes "optimized for different document formats." <https://www.llamaindex.ai/blog/rag-is-dead-long-live-agentic-retrieval> [verified]
- Anthropic (2025-09-29): hybrid of up-front curated context (CLAUDE.md-style) with just-in-time tools [verified, §1].

**Generic "throw docs at it" products (mid-2026) and their limits.**

| Product | What it does | Limits relevant here |
|---|---|---|
| Claude Projects RAG (support article updated 2026-03-16) | Auto-enables a "project knowledge search tool" when project knowledge exceeds the context window; ~10x capacity | No control over chunking, ranking, metadata or versions; consumer surface, not an API. <https://support.claude.com/en/articles/11473015-retrieval-augmented-generation-rag-for-projects> [verified] |
| Anthropic Files API + Citations (API) | Upload documents, reference by `file_id`, get char/page-located citations | It is document-in-context, not an index: you still choose what to put in the prompt. [verified via Anthropic docs] |
| OpenAI vector stores / file search | 800-token chunks, 400 overlap (100-4096 configurable); `ranking_options` with hybrid weighting and score threshold; attribute filters (≤16 keys); 512 MB / 5M tokens per file; 10 results default, 50 max; $0.10/GB/day beyond 1 GB | Chunk-level only, overlap default contradicts 2026 findings, 50-result cap limits agentic sweeps, attribute filtering is flat key/value—no version or thread model. <https://developers.openai.com/api/docs/guides/retrieval> [verified] |
| Cloudflare AI Search (formerly AutoRAG, renamed late 2025) | Managed R2→Vectorize pipeline with built-in MCP server | 4 MB file cap, 5 custom metadata fields, 10 KiB metadata/vector, first 64 bytes of strings filterable, no fine control of chunking/reranking. <https://developers.cloudflare.com/ai-search/platform/limits-pricing/> [verified] |
| Google Vertex AI RAG Engine (now under "Gemini Enterprise Agent Platform") | Managed corpora on RagManagedDb / Vector Search / Weaviate / Pinecone; hybrid search and reranking available | Preview outside US/EU, allow-listed regions, no data-residency/AXT; generic chunking. <https://docs.cloud.google.com/vertex-ai/generative-ai/docs/rag-engine/rag-overview> [verified] |
| LlamaCloud | LlamaParse + hierarchical/auto-merging indexes, 160+ connectors, credit pricing | "credit model becomes expensive at high document volumes" [secondhand, <https://forage.ai/blog/rag-as-a-service-platforms/>] |
| Ragie | $100-500/mo tiers; summary index, entity extraction, LLM rerank, filtering | Generic; no version/temporal model [secondhand, same source] |

**Why the generic products are a poor fit here [inference].** The corpus has three properties the products do not model: (1) *time and versions* (wiki history, book editions, dictionary changes) where the most-similar chunk is often the wrong edition; (2) *conversational structure* (threads, quoting, replies) where the unit of meaning is a thread or a Q&A pair, not a 800-token window; (3) *cross-source questions* ("the wiki says X, when was that decided on the list?") that need per-source indexes plus an agent that joins them. The 2026 evidence favours: per-source-type indexes (FTS + metadata; optional embeddings), thread/Q&A/version units, contextual headers naming source/date/version, a thin entity+timeline layer, an agent with a bounded loop, and an eval set drawn from the corpus itself.
